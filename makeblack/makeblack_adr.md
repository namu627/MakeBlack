# MakeBlack — ADR (Architecture Decision Records)

> 핵심 기술 선택의 이유를 기록한다. 나중에 팀원이 생기거나 기술 변경 논의 시 참고.

---

## ADR-001: React Native + Expo 선택

**날짜**: 2026년 3월
**상태**: 확정

### 결정
프론트엔드 프레임워크로 React Native + Expo를 사용한다.

### 고려한 대안
- Flutter
- 순수 React Native (Expo 없이)
- PWA (웹만)

### 이유
**Expo를 선택한 이유**
- iOS/Android/Web 동시 타깃이 가능
- EAS Build로 앱스토어 배포가 단순
- Expo Notifications로 푸시 알림 빠르게 구현
- 혼자 개발 시 설정 비용 최소화

**Flutter를 선택하지 않은 이유**
- 프로토타입이 이미 React로 되어 있어 이식 비용이 낮음
- Canvas 렌더링 로직(색상 수학, 픽셀 합성)이 JS로 작성되어 있음
- Dart 학습 비용 추가 불필요

**PWA를 선택하지 않은 이유**
- 푸시 알림이 iOS에서 제한적
- 홈 화면 위젯 불가 (향후 계획)
- 앱스토어 노출 불가

## ADR-002: Supabase 선택

**날짜**: 2026년 3월
**상태**: 확정

### 결정
백엔드로 Supabase를 사용한다.

### 고려한 대안
- Firebase
- 직접 서버 구축 (Node.js + PostgreSQL)
- PocketBase

### 이유
**Supabase를 선택한 이유**
- PostgreSQL 기반 → Row Level Security로 공개범위 서버단 구현 가능
- Realtime 기능 내장 → 팀 팔레트 실시간 동기화 핵심 기능 구현 가능
- Auth + DB + Storage + Edge Functions 통합
- 무료 티어로 MVP 검증 가능
- SQL 기반이라 복잡한 쿼리(통계, 집계) 작성 편리

**Firebase를 선택하지 않은 이유**
- NoSQL 구조라 관계형 데이터(팀-멤버-할일) 표현이 복잡
- Realtime은 Firebase도 되지만 RLS가 Supabase만큼 세밀하지 않음
- 비용 구조가 사용량 기반이라 예측이 어려움

**직접 서버를 선택하지 않은 이유**
- 혼자 개발 시 서버 운영/배포/보안 비용 과다
- MVP 검증 전에 인프라에 시간을 쏟을 필요 없음

## ADR-003: 팔레트 렌더링에 Canvas API 사용

**날짜**: 2026년 3월
**상태**: 확정

### 결정
팔레트 렌더링을 Canvas API (픽셀 단위 ImageData)로 구현한다.

### 고려한 대안
- CSS/SVG로 구현
- WebGL
- react-native-skia

### 이유
**Canvas를 선택한 이유**
- 픽셀 단위 제어로 실제 물감 번짐 효과 구현 가능
- 잉크 on water 알고리즘 (noise 기반 경계, 링 효과)이 Canvas에서 자연스럽게 구현됨
- 증분 렌더링 최적화 (WeakMap 캐시)로 성능 확보

**CSS/SVG를 선택하지 않은 이유**
- 픽셀 단위 noise 효과, 불규칙한 물감 경계 표현 불가
- 여러 drop의 색상 혼합을 픽셀 단위로 처리할 수 없음

**React Native에서는**
- `react-native-skia` 사용 예정
- 프로토타입의 Canvas 로직을 Skia API로 이식

## ADR-004: 개인 팔레트와 팀 팔레트 분리

**날짜**: 2026년 3월
**상태**: 확정

### 결정
개인 팔레트와 팀 팔레트를 완전히 분리한다. 팀 할일 완료가 개인 팔레트에 반영되지 않는다.

### 고려한 대안
- 팀 할일도 개인 팔레트에 반영

### 이유
- **의미의 명확성**: 개인 팔레트 = 내 하루의 달성감, 팀 팔레트 = 우리 프로젝트의 진행도
- **동기부여 설계**: 개인 팔레트가 팀 활동으로 채워지면 개인 목표와 팀 목표가 혼재됨
- 섞이면 두 팔레트 모두 의미가 애매해짐

## ADR-005: 팀 멤버 색상 자동 배정

**날짜**: 2026년 3월
**상태**: 확정

### 결정
팀 가입 순서대로 고유 색 계열을 자동 배정한다. 사용자가 직접 색을 선택하지 않는다.

### 고려한 대안
- 사용자가 직접 색 선택
- 랜덤 배정

### 이유
- **시각적 일관성**: 팔레트를 보면 누가 얼마나 기여했는지 바로 알 수 있어야 함
- **UX 단순화**: 색 선택 UI 없이 바로 팀에 참여 가능
- **예측 가능성**: 팀장은 항상 블루, 두번째는 항상 레드 → 반복 사용 시 직관적

## ADR-006: 감산혼합(CMY) 선택

**날짜**: 2026년 3월
**상태**: 확정

### 결정
팔레트 색상 혼합에 CMY 감산혼합을 사용한다.

### 고려한 대안
- RGB 평균 (가산혼합)
- HSL 공간 혼합

### 이유
- **RGB 평균의 문제**: 색이 많아질수록 밝은 회색이 됨. 흰색으로 수렴하여 BLACK 달성 컨셉과 반대
- **CMY 감산혼합**: 실제 물감처럼 색이 쌓일수록 어두워짐. BLACK으로 수렴하는 컨셉에 부합
- **사용자 기대**: "물감이 섞이면 어두워진다"는 직관과 일치

## ADR-007: 데이터 영속성 전략 (프로토타입 → 실서비스)

**날짜**: 2026년 3월
**상태**: Phase 1에서 구현 예정

### 결정
프로토타입에서는 React state(메모리)만 사용. 실서비스에서는 Supabase DB + 로컬 캐시 병행.

### 로컬 캐시 전략
```
AsyncStorage (Expo)
  └ 최근 30일치 할일/팔레트 캐시
  └ 오프라인 시 로컬 데이터 표시
  └ 온라인 복구 시 서버와 동기화

SecureStore (Expo)
  └ PIN 저장
  └ JWT 토큰 저장
```

### 이유
- 네트워크 없어도 기본 기능 동작
- 앱 재시작 시 로딩 없이 즉시 데이터 표시 (UX)
- 서버 장애 시 로컬 데이터로 fallback
